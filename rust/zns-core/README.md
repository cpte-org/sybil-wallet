# Offline ZNS signing core

`cargo test --manifest-path rust/zns-core/Cargo.toml` exercises this crate without building the Zcash wallet dependency graph. `cargo test --manifest-path rust/Cargo.toml --lib wallet::zns::tests` covers the real software-account and ZIP-316 boundary using temporary databases only.

The wallet derives its Base identity at **`m/44'/60'/<ZIP32 account index>'/0/0`** using the software account's BIP-39 mnemonic **and passphrase**. It reads the account index from wallet database derivation metadata, checks the seed fingerprint, and compares the complete re-derived Unified Full Viewing Key before deriving an EVM key. Database UUID changes and restore order do not change this identity. Different account indices produce different identities. Like standard Ethereum wallets, the address is shared between EVM chains; both transaction signatures and 7702 authorizations bind the configured chain ID. No UUID-derived or private-key export fallback exists.

The FRB API is in `rust/src/api/zns.rs`. All EVM amounts are unsigned decimal strings, calldata is `0x` hex, and JSON rejects unknown configuration/operation/transaction fields. The frontend obtains the existing encrypted software-account envelope, passes plaintext bytes for one operation, and clears its buffer. Rust zeroizes owned secret-envelope and seed buffers. Derived signing keys use RustCrypto's zeroizing key types. There is no stored EVM private key or generic destination/calldata signer.

`prepare` and `sign` admit only commit, exact registry approval, fixed-deposit registration, refresh, address update, vested-reward claim, position release, old-claims withdrawal, validated native-ETH-to-cbZEC Kyber swaps, and optional atomic registration. Management operations bind a stable position ID; `withdrawClaims()` does not release the current position. The required protocol ID binds the 365-day initial maturity, annual refresh, 90-day grace, full early-exit forfeiture and reserve-carry policy. Commitments additionally bind that protocol ID, registry, chain, name, Zcash address, registrant and secret. Prototype operations with a term in years are rejected.

Mainnet is fixed to Base 8453, canonical cbZEC and the verified Kyber router; Base Sepolia and local 31337 require `allowTestChain`. Configured maximum ETH input, token approval, gas limit, fee per gas and total estimated fee are checked before signing. Base's L1 fee is explicitly an estimate, not a protocol-enforced cap; EIP-1559 caps execution gas only. The frontend must review the account-scoped policy, verify the registry protocol and configured token, check the delegate bytecode, simulate the prepared call, and obtain fresh fees and nonce before signing.

Atomic registration encodes **`execute((address target,uint256 value,bytes data)[] calls,uint256 deadline)`** at the **owner's own address**, using the separately configured self-only delegate. It signs an EIP-7702 authorization for `transaction nonce + 1`; the outer transaction uses type `0x04`, pays its own gas, and contains exactly one authorization. All child calls revert together. This preserves `msg.sender` ownership in the ZNS registry. Delegation persists even when execution reverts; the frontend must disclose this and reject unexpected existing delegation. The commitment transaction remains separate because the registry enforces its 60-second minimum age.

The Kyber decoder checks canonical ABI, native source token, cbZEC destination, owner recipient, exact input, minimum return, empty permit/fee/source distribution arrays and supported flags. Mainnet pins the observed executor address `0x8f10b468b06c6fd214b65f87778827f7d113f996`. It does not interpret the executor's opaque route program or independently attest its code. Mainnet routing remains dependent on the configured router's verified semantics and the frontend's code/quote checks. Atomic execution additionally enforces the supplied deadline on chain. Standalone swaps require fresh local expiry checks and retain their router minimum-return protection if inclusion is delayed. Cross-chain Zcash funding is never atomic with Base execution.

Primary specifications checked while implementing:

- [BIP-32 specification and published vectors](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki)
- [RustCrypto BIP-32](https://docs.rs/bip32/0.5.3/bip32/) and [k256 0.13.4 ECDSA](https://docs.rs/k256/0.13.4/k256/ecdsa/)
- [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) and [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)
- [Verified Kyber router source](https://basescan.org/address/0x6131b5fae19ea4f9d964eac0408e4408b66337b5#code)

Tests include published BIP-32 extended keys, independent viem Ethereum account and Solidity commitment vectors, RLP decoding and signature recovery for both transaction types and the authorization, explicit chain binding, intent-limit failures, and hostile swap mutations. These are offline implementation checks, not evidence of a production registry deployment or a funded end-to-end registration.
